# 📘 CORE ARCHITECTURE DOCUMENT: ZERO-CLAW MIGRATION PIPELINE (HYBRID ARCHITECTURE)

## 1. Project Overview
The **Zero-Claw Migration Pipeline** is an automated, industrial-grade system designed to migrate legacy codebases (e.g., Node.js, Python) to modern frameworks.

Following a major architectural refactor, the system has transitioned from a brittle "One-shot JSON Generation" model to a robust **Hybrid Architecture**:
* **Rust (The Orchestrator):** Manages the async runtime (Tokio), guarantees atomic state safety (SQLite), parses Abstract Syntax Trees (Tree-sitter), and enforces strict isolated shadow testing (Docker Sandbox).
* **Python / OpenHands SDK (The Autonomous Engine):** Handles the reasoning and autonomous coding. Using the `TerminalTool` and `FileEditorTool`, it writes code, runs tests, and debugs directly on the disk like a real human software engineer.

**Architectural Benefits:** Completely eliminates JSON format exhaustion, bypasses LLM output token limits, and grants the AI the ability to self-verify its code before submission.

## 2. The 4 Core Agents

The system operates on a non-linear feedback loop orchestrated by four specialized agents:

### 2.1. Blueprinter (The Planner) - *Pure Rust*
* **Responsibility:** Ingests the legacy codebase, utilizing the `ASTParsingSkill` (Tree-sitter) to extract structures (functions, classes, imports). Calls the LLM via `zeroclaw` to formulate independent migration tickets.
* **Output:** An array of `Ticket` objects containing legacy code snippets and context.

### 2.2. Executor (The Builder) - *Rust 🤝 OpenHands*
* **Responsibility:** Translates legacy code to the modern framework and generates corresponding test cases.
* **Execution Flow:** 1. Rust compiles the Ticket context.
  2. Rust spawns the `openhands_worker.py` child process via `uv run python`.
  3. The OpenHands Agent autonomously creates and edits files directly in the `./modern_app/` directory.
  4. Rust scans the disk post-execution to register the generated files and passes the ticket to the Verifier.

### 2.3. Verifier (The Gatekeeper) - *Pure Rust*
* **Responsibility:** Ensures strict Semantic Equivalence. 
* **Execution Flow:** Generates mock JSON fixtures. Boots up isolated Docker containers (`--network=none`) for both the legacy and modern code. Compares the outputs (stdout, stderr, exit code, duration).
* **Output:** A `Verified` status or a detailed `ExecutionDiff` failure report.

### 2.4. Surgeon (The Debugger) - *Rust 🤝 OpenHands*
* **Responsibility:** Recursively fixes deep logic bugs caught by the Verifier.
* **Execution Flow:** 1. Rust packages the `ExecutionDiff` and `AstDiff` into a diagnostic prompt.
  2. Spawns a new OpenHands session.
  3. OpenHands uses its `TerminalTool` to run the failing tests and its `FileEditorTool` to patch the source code until the logic aligns.
  4. Returns the ticket to the Verifier for re-evaluation.

## 3. Rust ↔ Python Communication (Subprocess Protocol)

To ensure secure, deadlock-free, and lossless communication between the Rust Orchestrator and the Python Engine, the following strict protocols are enforced:

1. **Secure Temp Files (Context Passing):** * Rust NEVER passes prompts via CLI arguments due to OS length limits.
   * Rust uses `tempfile::NamedTempFile` to write prompts. The OS automatically deletes these files when the variable drops out of scope, preventing storage leaks.
2. **Environment Routing (Config Inheritance):**
   * The Rust `Command` explicitly passes LLM configurations (`LLM_MODEL`, `LLM_API_KEY`) to the Python subprocess. This ensures OpenHands strictly follows the Multi-Provider routing established by Rust.
3. **Timeout Guards:**
   * Every OpenHands subprocess call is wrapped in `tokio::time::timeout(Duration::from_secs(600), ...)`. This acts as a circuit breaker in case the Python Agent gets stuck in an infinite reasoning loop.
4. **Telemetry Synchronization:**
   * Before exiting (`exit 0`), the Python Worker dumps its total token usage and API costs (`llm.metrics`) to a `.usage_{ticket.id}.json` file.
   * Rust reads this file to update the `TicketTokenUsage`, ensuring the Audit Log remains perfectly accurate.
5. **Post-run File Scanning:**
   * Rust does not blindly trust predicted filenames. After Python exits, Rust uses `walkdir` to scan `modern_app/` and gather the actual `modern_file_paths` generated by the agent.

## 4. Ticket Lifecycle (State Machine)

The system persists state via an embedded SQLite database to support crash recovery.

* **`Todo`**: Newly generated by the Blueprinter. Waiting for a Semaphore permit.
* **Handoff**: `Todo` ➔ `ExecutorAgent` ➔ Transitions to `InProgress`.
* **`InProgress`**: Currently being evaluated by the `VerifierAgent`.
  * If Verifier passes ➔ Transitions to `Verified` (Terminal state).
  * If Verifier fails ➔ Transitions to `Failed(Reason)`.
* **`Failed`**: Ticket contains logical errors or execution crashes.
  * If `retries < MAX_SURGERY_RETRIES` (e.g., 3) ➔ Sent to `SurgeonAgent`. Once patched, returns to `InProgress` for re-verification.
  * If `retries >= MAX_SURGERY_RETRIES` ➔ Remains `Failed` (Terminal state). Requires human intervention.

## 6. Mandatory Technical Standards (Code of Conduct)

Any Engineer or AI Coding Assistant developing features for this repository **MUST** adhere to the following rules:

1. **Zero Network for Sandbox:** `SandboxSkill` executes untrusted LLM-generated code. The `--network=none` and `--cap-drop=ALL` flags MUST remain active during Phase 2 execution.
2. **No Sync Blocking in Async:** Never hold a `std::sync::MutexGuard` across an `.await` point in Tokio. This will immediately cause a thread-pool deadlock. Use `tokio::sync::Mutex` if asynchronous locking is required.
3. **Atomic State Upserts:** Any modification to a Ticket must be immediately committed to SQLite using an `UPSERT` statement to guarantee ACID compliance.
4. **Observable Subprocesses:** Calls to `openhands_worker.py` must consistently use `Stdio::inherit()` for Output/Error streams to maintain observability, allowing engineers to monitor the Agent's reasoning process in real-time.
